**Verdict**: agreement to ≥4 decimal places on lattice constants, ≥3 decimal
places on angles. Differences are ~10× tighter than typical PBE numerical
noise. Same physics, slightly different SCF iterate paths; both
converge to the same cubic basin.

### NaCl (CPU 0.75 vs GPU 1.0)

| Field | CPU | GPU | abs Δ | within tol? |
|---|---|---|---|---|
| a | 4.031914874 | 4.032545294 | 6.3e-4 Å | ✓ (tol 0.040 Å) |
| b | 4.031357610 | 4.032545294 | 1.2e-3 Å | ✓ |
| c | 4.033381858 | 4.032545145 | 8.4e-4 Å | ✓ |
| α | 60.01143° | 59.99999877° | 0.011° | ✓ |
| β | 60.01203° | 59.99999878° | 0.012° | ✓ |
| γ | 59.99543° | 60.00000000° | 0.0046° | ✓ |
| **sg** | **166 (R-3m)** | **225 (Fm-3m)** | mismatch | **✗ different crystal class** |

**The lattice constants agree to 3-4 decimals (~150 ppm)** — that's well
within the bench tolerance. But the *space group* differs because CPU's
cell has measurable a≠b≠c (Δ 1.2e-3 Å) and α≠β (Δ 0.011°). pymatgen's
`SpacegroupAnalyzer` thresholds at this level demote the cell from cubic
Fm-3m (#225) to trigonal R-3m (#166). The 0.25 lost on `space_group_number`
× 0.25 weight = exactly 0.25 below the perfect score.

**This is *not* a CPU vs GPU result-physics divergence** — it's
**LLM strategy variance**. Look at the input files each LLM wrote:

| | press_conv_thr | forc_conv_thr | etot_conv_thr |
|---|---|---|---|
| Si CPU | **0.05** ✓ | **1e-4** ✓ | default | 
| Si GPU | **0.05** ✓ | **1e-4** ✓ | default |
| **NaCl CPU** | **(unset → default 0.5)** ❌ | **(unset → default 1e-3)** ❌ | (unset) |
| NaCl GPU | **0.05** ✓ | **1e-4** ✓ | **1e-5** ✓ |

The v2 system prompt has an explicit "Cubic targets need tight convergence"
section recommending `press_conv_thr=0.05, forc_conv_thr=1e-4, etot_conv_thr=1e-5`.
Three of the four runs (incl. the **CPU** Si run) followed it. The NaCl CPU
run silently dropped the recommendation and used QE's loose defaults.
Same prompt, same model, same temperature → the failure is haiku
strategy noise, ~25 % rate on this rule (1/4 in this experiment, 1/2
across v1+v2 if you count v1's NaCl). The choice of CPU vs GPU is
irrelevant — it just happened to be the CPU run that dropped the rule
this time.

**Implication**: the 0.75 soft fail mode is not eliminated until the
recommendation is enforced *outside* the LLM (e.g., a hard-rule
template injection, or auto-augmenting any input file that misses
those keys). v3 lever.

## C. Selection guidance — when CPU vs GPU?

### From this experiment

- **Tiny tasks (≤ 2 atoms)**: wall is essentially equal (Si 239 s CPU vs
  250 s GPU; NaCl 333 s CPU vs 367 s GPU). Container startup overhead
  + per-call podman cold start eats GPU's compute advantage. **CPU
  marginally faster** on tiny systems.
- **Cost** is dominated by LLM turns (cache amortizes most of the prompt),
  not by backend; per-turn cost is LLM-bound. GPU may finish in slightly
  fewer turns when QE wall is short (less waiting → less polling) but
  this is noise on tiny systems.
- **Score** is path-independent. The 0.75 NaCl CPU is LLM-prompt
  compliance, not a backend issue.

### Synthesised with prior v1/v2 data + QEgpu.md §5.1 reference

| System size | Recommendation | Why |
|---|---|---|
| ≤ 2 atom cubic (Si, NaCl) | **CPU or GPU equivalent** | Container overhead ≈ raw compute; CPU often slightly faster wall |
| 3-15 atom (e.g. SiO2 quartz, 9 atom) | **GPU prefered** | v2 SiO2 CPU ran 45 min; GPU should be ~10-15 min |
| ≥ 16 atom (e.g. 16-atom Si supercell) | **GPU strongly prefered** | QEgpu.md §5.1: 7.6× SCF speedup, GPU util 95 % |
| ≥ 30 atom + d/f electrons (e.g. LiFePO4) | **GPU required** | v2 LiFePO4 CPU exceeded the 90 min harness cap; GPU should fit comfortably |
| Multi-iteration vc-relax (5+ BFGS steps) | **GPU prefered** | Container startup amortizes; pure compute dominates |

### What CPU vs GPU does **not** change

- Whether the task passes `audit_flags` (all 4 runs here hit 6/6)
- Whether the task scores 1.0 (LLM compliance is the binding constraint, not backend)
- Whether the LLM picks correct convergence thresholds
- Cost per turn (turn count is LLM-strategy-driven, not backend-driven)

### Practical default for this agent

For now, **default to CPU for tasks ≤ 2 atoms; GPU for everything else.**
This matches v1/v2 partition and minimises wall on the trivial cases
where GPU container startup is a relative tax. The bench harness lets
the operator override per-task via `QE_GPU_WRAPPER_DIR`.
